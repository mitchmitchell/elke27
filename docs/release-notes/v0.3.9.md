## What's Changed

### Bug Fixes

**Arming and disarming with a string PIN works again**

In 0.3.8, `Elke27Client.async_arm_area()` and `async_disarm_area()` raised
`Elke27ProtocolError: Operation failed` for every string PIN (for example
`pin="1234"`), and nothing was sent to the panel. The area generator module uses
`from __future__ import annotations`, so its `pin: int` annotation is the string
`"int"`; the client's PIN coercion compared it with `is int`, never converted the
PIN, and the generator then failed comparing a `str` with `0`. Raw
`async_execute("area_set_arm_state", pin="1234")` was affected the same way.

The coercion now resolves annotations with `typing.get_type_hints` and handles
`"int"` and `"int | str"` forms, so digit-string PINs are converted for generators
that take an int PIN and left unchanged for generators that also take `str`
(zone bypass).

**PIN format**

`area.set_arm_state` sends `pin` as a JSON integer (E27 Dealer API example
`"pin":1729`), so leading zeros cannot be represented on the wire: `"0123"` is
accepted and sent as `123`. An all-zero PIN (`"0000"`) maps to `0` and is
rejected with `Elke27InvalidArgument`, as are non-digit strings, `bool`, and
non-positive ints. `async_arm_area` and `async_disarm_area` now also accept int
PINs.
