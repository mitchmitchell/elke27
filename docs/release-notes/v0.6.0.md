## What's Changed

0.6.0 is a minor release (2026-11-17) with new public API: area entry/exit delay
state, arm night via Stay Instant, firmware capability fields, and stricter
snapshot publication after area and zone status reads. Read **Upgrade notes**
before upgrading integrations that arm at night or read area/zone status.

### New API

- **`AreaState.delay_state` and `DelayState` (#141).** Each area exposes
  `delay_state` as `DelayStateNone`, `DelayStateEntry`, or `DelayStateExit`.
  `AreaState.entry_delay` is true during entry delay; `AreaState.arming` is true
  during exit delay (derived from `delay_state`). Remaining seconds follow the
  panel's five-second status broadcasts only. Entry delay is simulator-proven
  only; hardware entry behavior is not claimed in this release.
- **`PanelInfo.application_firmware` and `AreaState.night_arm_supported`
  (#140, #142).** Application firmware from `control.get_version_info` and a
  per-area night-arm capability flag are on the public snapshot.
- **Exported delay types:** `DelayState`, `DelayStateNone`, `DelayStateEntry`,
  `DelayStateExit` (#141).
- **Arm night errors (#140, #142):** `Elke27PanelApplicationFirmwareUnknownError`,
  `Elke27NightArmFirmwareTooOldError`, `Elke27StayInstantRequiredError`.
- **Status publication (#144):** `Elke27SnapshotPublicationError` when snapshot
  replace fails during reply publication.

### Behavior

- **Arm night maps to Stay Instant (#140, #142).** `async_arm_area` with
  `ArmMode.ARMED_NIGHT` sends `area.set_arm_state` with `ARMED_STAY_INST`.
  Panel status `ARMED_STAY_INST` maps to `ArmMode.ARMED_NIGHT`.
- **Exit/entry delay reconciliation (#141).** Partial `area.get_status` payloads
  no longer clear `ee_timer` / `alarm_zone` on unrelated updates; exit-delay
  semantics follow documented fields and five-second ticks.
- **Status reads wait for snapshot publication (#144).** `async_execute` for
  `area_get_status`, `zone_get_status`, and `zone_get_all_zones_status` waits
  until the matching status is reflected in `get_snapshot()` or the command
  deadline expires. Ack-only `area_set_arm_state` or `zone_set_status` waits on
  the follow-up `area_get_status` or `zone_get_status`; when the write reply
  already includes confirmed status, publication wait applies to that reply.

### Upgrade notes

#### Arm night (Stay Instant)

- `ArmMode.ARMED_NIGHT` now sends `area.set_arm_state` with
  `arm_state=ARMED_STAY_INST` (Stay Instant), not a separate night wire mode.
  The panel must run application firmware **0.0.5.37 or later** (the `app` field
  from `control.get_version_info`, not SSP).
- Before the command is sent, if application firmware is not yet known,
  `async_arm_area(..., mode=ArmMode.ARMED_NIGHT)` raises
  `Elke27PanelApplicationFirmwareUnknownError` (subclass of `Elke27InvalidArgument`).
- If firmware is known and below 0.0.5.37,
  `Elke27NightArmFirmwareTooOldError` (subclass of `Elke27InvalidArgument`) is
  raised with `required` and `actual` version tuples.
- A panel refusal on the arm command still raises `Elke27PanelError` (subclass
  of `Elke27ProtocolError`) with `panel_error_code` and `reason`.
- If the panel accepts the write but Stay Instant did not take effect,
  `Elke27StayInstantRequiredError` (subclass of `Elke27Error`) is raised.
- If the panel accepts the write but the follow-up status refresh fails or does
  not confirm the outcome, `Elke27CommandOutcomeUnknownError` (subclass of
  `Elke27TimeoutError`) is raised with `route=("area", "set_arm_state")`.

#### New and related error classes

| Class | Subclasses |
| --- | --- |
| `Elke27PanelApplicationFirmwareUnknownError` | `Elke27InvalidArgument` (`ValueError`) |
| `Elke27NightArmFirmwareTooOldError` | `Elke27InvalidArgument` (`ValueError`) |
| `Elke27StayInstantRequiredError` | `Elke27Error` |
| `Elke27SnapshotPublicationError` | `Elke27ProtocolError` → `Elke27Error` |
| `Elke27PanelError` (arm rejections) | `Elke27ProtocolError` → `Elke27Error` |
| `Elke27CommandOutcomeUnknownError` (failed night refresh) | `Elke27TimeoutError` → `Elke27TransientError` → `Elke27Error` |
| `Elke27DisconnectedError` (publication wait failure) | `Elke27TransientError` → `Elke27Error` |

On `async_execute`, publication failures are `Result.error` (`ok=False`); they are
not raised. Typed command helpers raise via `_raise_v2_command_error` when they
inspect a failed `Result`.

#### Area and zone status reads

- After a successful reply for `area_get_status`, `zone_get_status`, or
  `zone_get_all_zones_status`, `async_execute` waits until kernel dispatch
  publishes the status into the client snapshot (`get_snapshot()`), bounded by
  the same command deadline used for the transport wait. The same wait applies to
  ack-only `area_set_arm_state` and `zone_set_status` through their follow-up
  status reads, and to arm or bypass replies that already include confirmed
  status.
- If the wait budget expires before publication completes, the command still
  returns `Result(ok=True, ...)` with the panel JSON payload; a WARNING is logged.
  Integrations that need a fresh snapshot should call `get_snapshot()` after the
  command returns or subscribe to status events.
- If the session is lost while waiting (for example panel disconnect),
  `async_execute` returns `Result(ok=False, error=Elke27DisconnectedError(...))`
  (for example message "Connection lost while waiting for snapshot publication.").
- If the client is closed while a command is waiting for publication, the
  in-flight `async_execute` returns `Result(ok=False, error=Elke27DisconnectedError)`
  (same pattern as other commands interrupted by teardown).
- If rebuilding the snapshot during publication fails, `async_execute` returns
  `Result(ok=False, error=Elke27SnapshotPublicationError)` (subclass of
  `Elke27ProtocolError`).
