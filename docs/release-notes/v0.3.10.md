## What's Changed

### Bug Fixes

**Panel rejections now say why** (#5)

When the panel answered a command with a non-zero `error_code` (wrong user code,
area not ready, area in alarm, zone not bypassable, ...), the client raised a
generic `Elke27ProtocolError("Operation failed.")` and the code was lost. It now
raises `Elke27PanelError`, a subclass of `Elke27ProtocolError`, with:

- `panel_error_code`: the E27 code (e.g. `11037`)
- `reason`: a short description (e.g. `"invalid user code"`)
- message: `Panel rejected the request: <reason> (error <code>).`

A warning with the command and code is also logged. Existing
`except Elke27ProtocolError` handlers keep working.

The panel answers a wrong user code on arm/disarm with `11004`; that reason reads
`"invalid parameter (check the user code)"`.

**Zone bypass works and reports rejections** (#10)

`async_set_zone_bypass` sent the PIN as a JSON string, which the panel answers with
`11008` (no authorization) even for valid codes. The PIN is now sent as a JSON
integer, validated the same way as arm/disarm (leading zeros dropped; all-zero,
non-digit, bool and non-positive PINs are rejected before sending). A `11008`
reply now raises `Elke27PanelError` with reason `"not authorized"` instead of the
generic "Operation failed.".

**Light state follows the panel** (#7)

The panel acks `light.set_status` with only `{light_id, error_code}`. The client
used to emit `LightStatusUpdated` with the cached (stale) state on that ack, and
`on` was only derived when it had never been set, so lights stayed off. The ack
now emits nothing. Whenever a status reply reports a `level`, `on` is set to
`level > 0` (`get_status` reports `level` but no `status`), so the follow-up
`get_status` updates the light. An explicit `status`/`state` field still wins.

**Area `ready` is populated** (#6)

`area.get_status` reports `ready_status` (`RDY_AWAY`, `RDY_STAY`, `RDY_NOT`), not a
`ready` boolean, so `AreaState.ready` was always `None`. It is now derived from
`ready_status`, which is also exposed as `AreaState.ready_status`.

**Arm night is rejected clearly** (#4)

The E27 supports Away and Stay arming; `area.set_arm_state` has no night state.
`async_arm_area(mode=ArmMode.ARMED_NIGHT)` used to fail with a generic
`Protocol error.`; it now raises `Elke27InvalidArgument` naming the unsupported
mode, before anything is sent.

### Diagnostics

Light status payloads are logged at debug level (`elke27_lib.handlers.light`).
