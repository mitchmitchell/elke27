## What's Changed

### Bug Fixes

**Panel rejections now say why** (#5)

When the panel answered a command with a non-zero `error_code` (wrong user code,
area not ready, area in alarm, zone not bypassable, ...), the client raised a
generic `Elke27ProtocolError("Operation failed.")` and the code was lost. It now
raises `Elke27PanelError`, a subclass of `Elke27ProtocolError`, with:

- `panel_error_code`: the E27 code (e.g. `11037`)
- `reason`: a short description (e.g. `"invalid user code"`)
- message: `Panel rejected the request: <reason> (error <code>).`

A warning with the command and code is also logged. Existing
`except Elke27ProtocolError` handlers keep working.

**Area `ready` is populated** (#6)

`area.get_status` reports `ready_status` (`RDY_AWAY`, `RDY_STAY`, `RDY_NOT`), not a
`ready` boolean, so `AreaState.ready` was always `None`. It is now derived from
`ready_status`, which is also exposed as `AreaState.ready_status`.

**Arm night is rejected clearly** (#4)

The E27 supports Away and Stay arming; `area.set_arm_state` has no night state.
`async_arm_area(mode=ArmMode.ARMED_NIGHT)` used to fail with a generic
`Protocol error.`; it now raises `Elke27InvalidArgument` naming the unsupported
mode, before anything is sent.

### Diagnostics

Light status payloads are logged at debug level (`elke27_lib.handlers.light`) to
capture the panel's field names for #7.
